# Sael 网关设计

> 本文描述网关和运维界面。Sael 现有 CLI 负责提出 11 个审核问题并返回分数；网关负责提取当前用户文本，再按运维配置的场景条件和优先级决定记录并放行或记录并拦截。文中的界面数字都是示意，不代表默认阈值或真实性能。

## 1. 目标与边界

### 1.1 要实现什么

客户端把 AI 请求发送给 Sael 网关，网关在转发到目标站前读取本次请求中**当前用户提交的文本**。Sael 返回每个审核项的分数后，网关按场景逐条比较条件：

- 每个场景条件直接保存审核项和它自己的原始分数阈值，分数严格超过该阈值才满足条件。
- 一条场景选择“满足任一项”或“满足全部项”，并指定“记录并放行”或“记录并拦截”。多条场景同时匹配时，只执行列表中最靠前的那条。
- 没有任何场景匹配时直接转发，不生成逐请求记录。

九个 `noul` 问题的分数范围是 0–1；`sexual`、`gore` 两个 `score` 问题的范围是 0–3。阈值只能在具体场景条件中配置，网关不对分数加权。

### 1.2 审查范围

- 只审**本次请求中最后一个当前用户输入**的文本。历史 user 消息、system/developer 指令、assistant 消息和工具结果都不计入本次审查。
- 文本与图片混合时只提取文本；图片、音频、视频、文件内容本身不审查。纯非文本请求记为“无可审文本”，继续转发，不显示为“审核通过”。
- 不修改请求正文，不转换协议，不做响应侧审查；流式响应按上游协议透传。
- 不做命中 hash 复用、分数加权、人工复核系统、灰度拦截决策台或固定容量上限。这些都不是这条主流程所需的组件。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 可审请求 | 成功提取到当前用户文本，且审查总开关已开启的请求 |
| 已审查 | Sael 成功返回本次请求所需的审核结果 |
| 场景条件满足 | 场景中该审核项的分数严格大于该条件自己的阈值 |
| 场景匹配 | 一条场景规则的条件被本次审核项命中集合满足 |
| 生效场景 | 多条场景匹配时，优先级最高、实际决定处理动作的那条 |
| 仅记录命中 | 生效场景要求放行；写命中记录并转发 |
| 拦截命中 | 生效场景要求拦截；写命中记录并拒绝 |
| 未审放行 | 可审请求因分类器错误或超时未得到结果，按故障策略转发 |
| 无可审文本 | 合法请求没有符合当前用户文本边界的内容；不调用 Sael |

## 2. 网关框架设计

### 2.1 组件和依赖

```text
客户端
  │  OpenAI Chat / Responses、Anthropic Messages、Gemini generateContent
  ▼
sael-gateway（Go）
  ├─ 协议路由与正文提取
  ├─ 请求参数采集
  ├─ 审查编排：Sael 分数 → 当前规则 → 记录/拦截
  ├─ 上游 HTTP 代理
  ├─ 管理 API 与分钟统计
  └─ 内嵌 React 运维界面
       │              │                 │
       ▼              ▼                 ▼
    sael CLI      PostgreSQL         既有 AI 上游
    （调用 SDK）   规则/记录/统计      （原协议转发）
```

- **网关**负责 HTTP 生命周期、协议提取、阈值和动作、记录、管理 API。它不复制 CLI 中审核问题的文字和判据。
- **Sael CLI**仍是问题集的来源。网关通过 `sael check --json` 提交当前用户文本并读取分数；调用封装在 `Classifier` 接口后。CLI 的可执行文件和配置由部署提供。
- **PostgreSQL**保存运维规则、命中/故障事件、仪表盘所需的时间桶计数和规则变更记录。
- **React 界面**由网关提供，所有管理请求走同源的 `/admin/*` API。管理路由与代理路由分开鉴权。
- 本设计不依赖 Redis。没有 hash 复用或配置广播，自然不需要为它额外部署一个容器。

网关作为仓库中的独立 Go 模块放在 `gateway/`，与现有 `cli/`、`sdk/` 并列。依赖方向是“网关调用 CLI 可执行文件，CLI 使用 SDK”。

### 2.2 一次请求怎样走

```text
接收请求
  → 识别协议、读取原始 body
  → 提取当前用户文本和关键参数
  → 读取一次当前规则快照
  → 有文本且总开关开启：调用 Sael，逐项比较阈值，得到命中项集合
      ├─ 命中项非空 → 按优先级找到第一条匹配的场景
      │    ├─ 动作为“拦截” → 写命中记录 → 返回对应协议的拒绝响应
      │    └─ 动作为“放行” → 写命中记录 → 转发原请求
      │    没有场景匹配 → 按“未匹配命中处理”记录并放行或记录并拦截
      ├─ 没有审核项命中 → 转发原请求
      └─ 调用失败 → 计入未审放行并记录故障 → 转发原请求
  → 无可审文本或总开关关闭：计数并转发，不记为已审查
```

审查、场景匹配和命中记录发生在上游拨号前；“拦截命中”不应到达上游。转发使用原始 body、原请求路径和查询参数，响应状态、正文及 SSE 数据流由代理透传。网关可以按 HTTP 代理规范处理必要的连接级 header，不能承诺网络传输层的字节完全相同。

每次请求只使用一个策略版本。即使管理员在分类器调用期间修改了阈值、场景或顺序，该请求仍按进入审查时取得的快照完成判定，并把版本写入事件。

### 2.3 当前用户文本提取

| 协议 | 路由 | 本次审查取的文本 |
|---|---|---|
| OpenAI Chat Completions | `POST /v1/chat/completions` | `messages` 最后一条必须为 `role=user`；读取字符串 `content` 或其中的文本 part |
| OpenAI Responses | `POST /v1/responses` | `input` 是字符串时直接取；是数组时只读取最后一个当前用户输入项中的文本 |
| Anthropic Messages | `POST /v1/messages` | 最后一条当前 `user` 消息的文本 block；忽略 `tool_result`、图片等非文本 block |
| Gemini | `POST /v1beta/models/*:generateContent` 与 `*:streamGenerateContent` | `contents` 最后一个 `role=user` 内容的 `parts[].text` |

提取器按明确的协议和字段解析，不从整个 JSON 中搜索任意 `text` 字段。`previous_response_id` 等服务端保存的历史上下文不在本次审查范围内。字段合法但没有当前用户文本时，计为“无可审文本”；JSON 格式错误时由网关按协议返回 400。提取器返回文本以及 `has_non_text_input`，后者只供运维说明“本次仅审了文本”，不改变阈值判定。

sub2api 的 `content_moderation_input.go` 提供了“只看最后一次用户输入”的参考实现。本设计借用这个**提取边界**，不借用它面向其他业务的图片审核和通用兜底扫描。

### 2.4 关键请求参数

网关直接从本次请求取得并记录：

| 参数 | 来源 | 用途 |
|---|---|---|
| `request_id`、时间 | 网关生成或接收可信入口提供的 ID | 排障与日志关联 |
| `protocol`、`endpoint` | 命中的路由与原请求路径 | 区分客户端协议 |
| `model` | body 中的模型字段；Gemini 可从路径取得 | 查某个模型上的命中 |
| `stream` | body 的流式标志或 Gemini 流式路由 | 区分普通请求与 SSE |
| `user_id`、`api_key_id`、`group_id` | 仅来自可信前置系统或明确的集成接口 | 按主体定位；取不到就留空 |
| 主体显示名、API Key 名、分组名 | 仅来自同一可信入口，且字段确实存在时 | 方便运维识别记录；不保存凭证本体 |
| `upstream_name` | 网关当前选用的上游配置 | 定位转发目标，不保存上游密钥 |

不要把客户端自己传的任意用户 ID header 当作已验证身份，也不要把 `Authorization` 的完整值写入记录。sub2api 的审核输入确实包含 request ID、用户/API Key/分组、端点、模型、协议和原 body；独立部署的 Sael 网关只有在入口提供可信身份时才能得到其中的主体字段。

### 2.5 阈值、场景与优先级

**第一步：逐项判断命中。** 每个审核问题在运维平台配置一个阈值：

| 字段 | 含义 |
|---|---|
| `question` | CLI 返回的问题键 |
| `answer_type` | `noul` 或 `score`，决定输入范围和界面单位 |
| `threshold` | 分数严格大于此值才命中；noul 为 0–1，score 为 0–3 |

网关只保存问题键和类型，以便校验规则和绘制设置表；审核问题的文字及判据仍只在 CLI 中。CLI 返回的键或类型与当前规则不符时，整次审查记为“不可用”，不能把缺失项当成零分。

**第二步：匹配场景。** 管理员可以建立多条场景规则，每条包含名称、审核项列表、匹配方式（“满足任一项”或“满足全部项”）、处理动作（“记录并放行”或“记录并拦截”）和优先级。每条规则至少选择一个审核项；条件只看这些审核项是否已超过各自阈值，不比较或合并原始分数。

“满足任一项”表示所选问题中至少一个命中；“满足全部项”表示所选问题全部命中。请求还命中了其他问题时，不影响这条场景的匹配结果。

场景在设置页按**从上到下、由高到低**排序。依次检查，只采用第一条匹配规则的动作；其余匹配规则可以在事件详情中列出，但不参与本次决定。没有场景匹配而已有审核项命中时，执行设置页的“未匹配命中处理”，它同样只能是“记录并放行”或“记录并拦截”。没有审核项命中时，直接转发且不写逐请求命中事件。

例如，把“同时命中 A 和 B → 记录并放行”排在“命中 A 或 B → 记录并拦截”之前：

| 本次命中项 | 第一条匹配场景 | 结果 |
|---|---|---|
| A | A 或 B | 记录并拦截 |
| B | A 或 B | 记录并拦截 |
| A、B | A 和 B | 记录并放行 |

任何审核项命中都会生成**一条请求级命中事件**，其中列出全部命中项及其分数、阈值，生效场景或未匹配命中处理，以及最终动作。同一请求只算一次“命中请求”，按问题或场景统计时按各自口径计数。审查总开关只负责整体启停；关闭时所有请求原样转发，仪表盘显著显示“审查已关闭”。阈值、场景组合、动作、排序和未匹配命中处理都在运维平台配置，不写死在代码里。

### 2.6 失败和资源约束

- 分类器超时、进程启动失败、返回无法解析或缺少配置中的问题时，本次结果为“不可用”，不按零分处理，不产生假命中。请求按当前故障策略放行，仪表盘计入“未审放行”。
- 网关为 CLI 调用设置总期限和并发上限；等待并发槽也受期限约束。超时或队列拥挤要计数，不能在界面上显示成“审核通过”。
- PostgreSQL 写命中或故障事件失败时，把同一条去敏事件写入本地文件，恢复后补入 PG；同时计入写库失败指标。若本地兜底也失败，保留错误日志并显著告警，不能让界面把缺失记录显示成“没有命中”。记录故障不改变已经算出的拦截或转发动作。
- 管理 API 需要独立鉴权。分类器凭证、上游凭证与管理员会话都不进入事件表或前端响应。

### 2.7 存储和项目目录

**存储分工**

| 数据 | 保存内容 | 用途 |
|---|---|---|
| `gateway_policy` | 总开关、11 项阈值、有序场景规则、未匹配命中处理、版本、修改人和时间 | 请求判定与设置页 |
| `audit_events` | 命中事件与审查失败事件；请求参数、去敏文本预览、分数与阈值、生效场景、策略版本、最终动作、错误类别 | 命中查询与排障；PG 故障期间先写本地兜底文件 |
| `gateway_counts_minute` | 每分钟的请求、可审、成功、命中、拦截、未审放行、无可审文本计数 | 运维仪表盘 |
| `policy_changes` | 阈值、场景、顺序或未匹配命中处理变更前后的值、操作者、时间 | 设置页的最近修改 |

正常未命中请求不写逐请求事件；仪表盘总量来自分钟计数，避免把“没有命中记录”误解成“没有流量”。命中事件只存当前用户文本的**去敏预览**，不存完整请求 body 或明文密钥。预览的长度、保留时间由设置页配置；**没有 10GB 容量上限**。

```text
gateway/
├── cmd/sael-gateway/       启动、装配与优雅停机
├── internal/
│   ├── protocol/           四种请求格式的当前用户文本提取
│   ├── audit/              CLI 适配、阈值命中与有序场景匹配
│   ├── proxy/              上游转发与协议错误响应
│   ├── record/             命中/故障事件、兜底文件与分钟计数
│   ├── admin/              仪表盘、记录、规则 API
│   ├── store/              PostgreSQL
│   └── config/             部署配置与生效规则快照
├── web/                    React 源码与构建产物
├── migrations/
└── deploy/
```

部署包含网关、PostgreSQL，以及打包在网关镜像中的 `sael` CLI。上游地址、Sael 凭证、CLI 路径和并发/超时预算属于部署配置；运维界面展示其生效状态，但不假装修改了部署环境。问题阈值、场景规则、顺序和未匹配命中处理由运维界面修改并热生效。

## 3. 前端 UI 设计

### 3.1 信息架构与视觉原则

左侧只保留三个主入口：**总览、命中记录、设置**。总览回答“现在有没有在审、哪些场景生效、是否漏审”；记录页回答“哪条请求命中了什么、由哪条场景决定处理”；设置页配置问题阈值、场景条件、动作和优先级。

- 顶栏在所有页面固定展示审查总开关状态、场景规则数、分类器状态和当前策略版本。审查关闭或分类器不可用时显示文字告警，不只靠颜色。
- 主内容区域按“关键状态 → 趋势 → 下钻”排布。关键数字旁写清时间范围与口径；点击数字进入带相同筛选条件的记录页。
- 以中性灰作页面底色，蓝色用于操作，琥珀色用于未审放行，红色用于真实拦截和故障。标签同时使用文字与图标。
- 桌面端优先保证 1280px 宽度下可读；窄屏把统计卡排成两列或一列，记录表保留必要列并让详情在独立抽屉中展示。


图中的数字只是排版示例。页面固定采用以下口径：

| 指标 | 算法和展示方式 |
|---|---|
| 进入审查路由 | 该时间窗进入受支持路由的请求数 |
| 可审请求 | 总开关开启、格式有效、成功提取当前用户文本的请求数 |
| 成功审查 | 可审请求中 Sael 完整返回结果的次数 |
| 命中请求 | 成功审查且至少一个问题超过阈值的请求数；一次请求只计一次 |
| 实际拦截 | 生效场景或未匹配命中处理要求“记录并拦截”的请求数 |
| 未审放行 | 可审但 Sael 未给出可用结果、最终转发上游的请求数 |
| 无可审文本 | 受支持路由中没有当前用户文本的次数，单独展示 |
| 审查成功率 | 成功审查 ÷ 可审请求；可审请求为 0 时显示“暂无可审请求” |

**页面状态**：

- 审查总开关关闭：顶部常驻“审查已关闭，当前请求直接转发”；成功率显示“未启用”，不能显示为 100%。
- 分类器错误或未审放行大于 0：首屏显示醒目提示，并可进入故障记录；同时展示数据最后更新时间。
- 当前窗口无流量：显示“该时间段没有请求”，不画全零趋势来暗示系统健康。
- PG 指标暂时不可用：显示“统计暂不可用”和最后成功更新时间，不用 0 代替缺失值。

最近命中只显示命中或故障事件，避免大量正常请求淹没。“生效场景”每次最多一条，场景统计之和加上“无场景匹配”才等于命中请求数；切换到“按问题查看”时，一次请求可计入多个问题，图旁需注明不可把条形图相加当作请求数。

### 3.3 命中记录

列表的默认筛选是近 24 小时，展示命中事件；可切换到“审查失败”。常用筛选放在一行：时间、处理结果（记录并放行/记录并拦截/失败）、生效场景、关键词或请求 ID。命中问题、协议、模型和可信主体放进“更多筛选”。

| 列 | 内容 |
|---|---|
| 时间 | 本地时间，悬浮显示完整时间戳 |
| 处理结果 | “仅记录并转发”“已拦截”“未审放行” |
| 命中项 | 问题名及 `分数 > 当时阈值`；多个命中项可展开 |
| 生效场景 | 场景名称、当时优先级；无匹配时显示“未匹配场景，按默认动作处理” |
| 请求 | 协议、模型、接口、是否流式 |
| 主体 | 仅展示实际获得的可信用户/API Key/分组标识 |
| 请求 ID | 一键复制，用于与上游日志对照 |

点击一行打开详情抽屉。上半部分先放**最终动作、生效场景与优先级、条件匹配情况**，再放去敏后的当前用户文本、请求参数、11 项分数与当时阈值、策略版本、分类器耗时及错误。若有其他场景也匹配，注明它们因优先级较低而未生效。没有拿到的主体字段显示“未提供”。正常未命中请求没有逐请求详情。

### 3.4 设置：问题阈值与场景规则

设置页把“何时命中”和“命中后如何处理”分成两个紧邻的区块。第一块设置 11 个问题各自的阈值，第二块组合这些命中项并排序；动作只设置在**场景**和“未匹配命中处理”上，不再设置在单个问题上。

```text
┌────────────────────────────────────────────────────────────────────────────────┐
│ 设置 / 审查策略                                      当前生效 v12   [查看变更]  │
├────────────────────────────────────────────────────────────────────────────────┤
│ 审查总开关  [开启 ●]       场景 2 条 · 拦截 1 条 · 放行 1 条                     │
│                                                                                │
│ 审核项阈值                  分数严格大于阈值，才算该项命中                      │
│ cyber_abuse     概率 0–1      [0.85]                                            │
│ illicit         概率 0–1      [0.90]     ... 其余 7 个 noul 问题                │
│ sexual         量表 0–3      [2.00]                                            │
│ gore           量表 0–3      [2.00]                                            │
│                                                                                │
│ 场景规则（从上到下，先匹配先执行）                              [新增场景]   │
│ 1  ≡  例外：A 和 B           满足全部 [A, B]  → 记录并放行   [编辑] [删除]   │
│ 2  ≡  常规：A 或 B           满足任一 [A, B]  → 记录并拦截   [编辑] [删除]   │
│    拖动场景左侧把手调整优先级；同时命中 A、B 时第 1 条生效。                  │
│                                                                                │
│ 未匹配命中处理    (●) 记录并放行   ( ) 记录并拦截                               │
│ Jev 文本调试      输入当前用户文本 → 11 项分数 → 模拟场景动作                  │
│                                                                                │
│ 未保存改动：阈值 1 项 · 场景排序 1 处                 [放弃] [保存并生效]      │
├────────────────────────────────────────────────────────────────────────────────┤
│ 运行与连接  上游地址 · CLI 版本 · 分类器模型 · 最近连通结果 · 超时/并发         │
│ 记录设置    去敏预览长度 · 记录保留天数 · 最近清理时间                           │
│ 最近修改    时间 · 操作人 · 阈值/场景/优先级/默认动作改动                       │
└────────────────────────────────────────────────────────────────────────────────┘
```

图中场景名和数值仅说明交互，不代表默认阈值或真实性能。真正初始阈值与“未匹配命中处理”应在部署规则中明确给出。

**场景编辑器**由四项组成：场景名称、选择的审核项（至少一项）、匹配方式（“满足任一项”或“满足全部项”）、处理动作（“记录并放行”或“记录并拦截”）。场景可增删、编辑和排序；不提供嵌套条件。列表的第 1 条优先级最高，保存后顺序成为策略的一部分。优先级通过每条场景左侧的拖拽把手调整，键盘用户可用 Alt+↑/↓ 移动。

**Jev 文本调试**位于“设置 → Jev 连接与调试”：管理员保存接口地址、模型 ID 和 API Key 后，直接输入一条当前用户请求文本。调试调用已保存的 Jev 配置，返回 11 项原始分数，并按当前阈值和场景计算模拟动作；不请求生产上游、不写入事件、不计入生产统计，也不保存调试文本。策略尚未配齐时仍显示原始分数，并明确提示不能模拟最终动作。

**编辑与保存行为**：

1. `noul` 阈值只接受 0–1，`score` 只接受 0–3；保留小数，不把量表分数当成概率。页面始终展示“严格大于阈值才命中”。
2. 场景至少选择一个审核项，必须选定“满足任一项／满足全部项”和处理动作。多场景重叠是允许的，实际动作只取排序最靠前的匹配场景；页面通过拖拽场景把手调整顺序，键盘用户可用 Alt+↑/↓ 移动；页面始终展示这条规则，避免误以为动作会合并。
3. 修改阈值、场景条件、动作、排序或未匹配命中处理后，页面显示未保存状态和逐项差异；保存时一次提交整份策略，服务端校验后产生新版本。
4. 新增拦截场景、把放行改为拦截、改变可能覆盖已有场景的顺序，或关闭总开关时，保存前展示具体变更并要求确认。不展示未经数据支持的“预计误拦量”。
5. 管理员同时编辑时，用策略版本拒绝覆盖较新的内容；提示重新载入，并保留本地尚未提交的改动供核对。
6. 上游地址、CLI 路径、模型、凭证和调用预算属于部署配置。此页显示生效值与连通性，密钥只显示“已配置/未配置”，不能读回明文。
7. 记录设置只涉及去敏预览长度和保留天数；没有容量上限控件、复杂清理顺序或原文导出开关。

设置页下方的最近修改保留时间、操作者、旧值、新值和生效版本。命中事件保存当时的阈值、场景顺序、未匹配命中处理和最终动作；后来改规则不会改写旧事件的解释。

### 3.5 共用交互

- 总览的“实际拦截”“仅记录命中”“未审放行”都能进入带对应筛选的记录页；从详情返回时保留时间范围和筛选条件。
- 列表、图表、设置页都要有加载、空数据、请求失败三种明确状态。自动刷新不能覆盖正在填写的设置表单。
- 设置表单使用明确文字标签、键盘可操作的输入和可见焦点；状态不只用红/绿颜色表达。
- 所有页面默认简体中文，时间窗和统计口径靠近数字展示，不让用户猜分母。

## 4. 管理 API 与数据契约

管理 API 与代理路径隔离，所有读取敏感事件或改规则的接口都需要管理员身份。

| 接口 | 返回或操作 |
|---|---|
| `GET /admin/overview` | 所选时间窗的指标、趋势、按问题命中量、数据更新时间 |
| `GET /admin/events` | 命中/失败记录的分页与筛选 |
| `GET /admin/events/{id}` | 一条事件详情、分数、当时阈值及去敏文本 |
| `GET /admin/policy` | 当前总开关、11 项阈值、有序场景列表、未匹配命中处理及策略版本 |
| `PUT /admin/policy` | 带旧版本号保存整份策略，返回新版本；版本冲突返回 409 |
| `GET /admin/jev` | Jev 地址、模型、密钥是否已配置；不返回密钥明文 |
| `PUT /admin/jev` | 保存 Jev 地址、模型和 API Key；三项不完整时拒绝保存 |
| `POST /admin/jev/test` | 用输入文本调用 Jev，返回 11 项分数和当前策略模拟结果；不产生生产副作用 |
| `GET /admin/runtime` | Jev 连通状态、固定上游地址、并发和最近错误 |
| `GET /admin/policy-changes` | 最近规则修改记录 |

`gateway_counts_minute` 由网关内部计数器按分钟写入 PG。统计维度先保留时间和协议；模型筛选需要模型维度的计数，模型名可按实际请求写入同一聚合表。事件列表只查 `audit_events`，不能拿它当所有请求的分母。

审查事件保留以下足够排障的字段：时间、请求 ID、协议、接口、模型、流式标记、可得的可信主体、去敏文本预览、全部返回的分数、命中问题及其阈值、生效场景与当时优先级、未匹配时采用的默认动作、策略版本、最终处理、分类器耗时和错误类别。数据库不保存客户端或上游的明文凭证。

## 5. 验收场景

| 场景 | 预期 |
|---|---|
| 当前用户文本未超过任何阈值 | 上游收到原请求；成功审查计数增加；不产生逐请求命中事件 |
| 仅 A 命中，低优先级的“A 或 B”场景要求拦截 | 写一条命中事件；按客户端协议拒绝；上游没有收到请求 |
| A、B 同时命中，高优先级的“A 和 B”场景要求放行 | 写一条命中事件，列出 A、B 和生效场景；上游收到原请求 |
| 两条场景都匹配且动作冲突 | 只采用列表中排序最靠前的场景；事件记录生效场景和最终动作 |
| 调换上述两条场景的顺序 | 相同 A、B 命中集合改由“A 或 B”场景处理；策略版本更新 |
| 有审核项命中但没有场景匹配 | 写一条命中事件；使用设置页配置的“未匹配命中处理” |
| 只存在历史消息、工具结果或非文本输入 | 不调用 Sael；计为无可审文本；按原协议转发 |
| 分类器超时或返回缺失项 | 计为未审放行并留下故障记录；不显示为未命中 |
| 运维修改阈值、场景、顺序或默认动作 | 新请求使用新策略；旧事件仍显示当时的策略快照 |
| 流式请求命中拦截 | 在连接上游、返回 SSE 首字节前拒绝 |
| 流式请求不拦截 | 上游响应按原协议持续透传 |

## 6. 实现依据与待确认数据

- sub2api 的当前用户提取参考：[`content_moderation_input.go`](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/content_moderation_input.go)。请求上下文字段参考：[`content_moderation.go`](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/content_moderation.go)。它另有全对话扫描路径，本设计不采用。
- Sael 的实际答案形状和问题集见仓库的 `cli/internal/cli/output.go`、`cli/internal/questions/moderation.go` 与 `sdk/answers.go`。TypeSafe 官方分别定义了 [Noul](https://docs.typesafe.ai/primitives/noul) 和 [Score](https://docs.typesafe.ai/primitives/score) 的取值语义。
- 代理行为按 Go [`httputil.ReverseProxy`](https://pkg.go.dev/net/http/httputil#ReverseProxy) 的 HTTP 语义设计。四种协议的提取路径应以各自官方 API 文档和真实请求样本验证。

落地前仍需给出两类业务数据：**各项初始阈值、初始场景顺序和未匹配命中处理**，以及**命中记录需要保留的去敏文本长度和天数**。这些数值不从旧文档的示意图抄作默认值。
