# 网关性能审查与改造

日期：2026-09-25。目标为 **5,000 RPS**，验收网关自身，压测以固定响应替代外部分类服务。模型容量、服务配额和模型推理优化不属于本次范围。

## 行为边界

- 正常请求只保留必要聚合，不保存逐条审核记录、正文或分类分数分布。
- 场景命中、审查失败、输入超限及会话冻结等异常保留记录，文本持久化前去敏。
- 端点、模型、阈值、规则顺序、转发报文与流式行为保持兼容。
- 不增加业务请求并发限制、不新增请求体大小限制。
- Redis 是部署必需组件；PostgreSQL 保留配置与历史数据。

Apple M2，8 核、16 GB 内存；Go 1.26.5。PostgreSQL 17 运行在 Docker Desktop，数据来自独立测试库。每组 3 次、每次约 600 ms，以下为中位数。本地微基准不能直接作为整机 RPS 验收。

| --- | ---: | --- |
| 读取策略、分类连接和出站配置 | 0.895 ms | 3 次数据库往返；现有缓存仅在故障时生效 |
| 普通请求统计写入，串行 | 1.283 ms | 每请求事务与聚合行更新 |
| 普通请求统计写入，并行 | 0.953 ms | 约 1,050 次 / 秒的总吞吐，热点计数行形成串行等待 |

## 已完成的改造

- **正常请求**：不构造审核事件，不做无用的去敏，不保存逐条正文、分数分布或场景明细。只保留计数、比例分母、耗时和 RPM 所需的聚合。首页取消“完成审查”独立卡片及“未匹配放行”占比。
- **异步写入**：请求进入容量 4,096 的内存队列；后台最多等待 2 ms 或收集 128 项后合并，写入 Redis Streams。队列满时背压，不采样丢弃。数据库消费者批量合并后提交，正常退出会排空内存队列。
- **恢复与去重**：Redis 断线时批次刷盘到本地暂存。生产者按序号发布，丢失确认后可重试；数据库统计、异常记录和消费位置在同一事务中提交。数据库只保存一个消费位置，不为正常请求建立逐条去重表。积压只在提交后清理，不按队列长度截断。
- **配置**：PostgreSQL 保存设置，请求读取进程内快照。Redis 通知加速同步，每秒核对数据库，修复漏通知和断线造成的差异。
- **会话冻结**：使用 Redis TTL，迁移尚未过期的旧冻结，保持凭据隔离、到期释放、重试不续期。
- **实时 RPM**：在分类前按秒聚合进网数量，只保留约两分钟 Redis 数据。顶部取最近 60 个完整秒，跟随端点和模型筛选，每 10 秒刷新；不显示峰值。历史曲线按各桶实际时长换算 RPM。
- **请求路径**：复用转发对象、HTTP 连接和 32 KB 缓冲；短文本通过安全的字节上界跳过分词。去敏先筛选必要的模式，保留原有规则及 Unicode 大小写匹配行为。
- **分类接入**：网关默认复用进程内 SDK，取消逐请求启动 CLI。问题集移动到共享的 `sdk/moderation`，CLI 使用同一份定义；原有金样测试保持通过。外部模型未做改动。

## 5,000 RPS 验收

真实 HTTP → 网关 → 固定分类 HTTP 响应 / 转发 HTTP 服务，启用真实 Redis 和 PostgreSQL。负载生成器、网关及两个固定响应服务在同一个本机 Go 进程中；数据库运行于 Docker。下表包含调度等待、HTTP、SDK、入队和响应时间，不包含外部模型推理。负载生成有 256 个工作协程，这不是网关并发上限。

| 流量 | 时长 / 请求数 | 实测 RPS | P50 | P95 | P99 | HTTP 错误 | 逐条记录 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 KB，95% 正常 / 5% 拦截 | 20 s / 100,000 | 4,999.97 | 0.43 ms | 4.74 ms | 71.48 ms | 0 | 5,000 |
| 1 KB，全部拦截 | 30 s / 150,000 | 4,999.94 | 0.45 ms | 5.41 ms | 76.34 ms | 0 | 150,000 |
| 1 KB，SSE 透传 | 10 s / 50,000 | 4,999.91 | 0.46 ms | 4.18 ms | 20.92 ms | 0 | 0 |
| 16 KB，正常审查 | 10 s / 50,000 | 4,999.76 | 4.31 ms | 88.76 ms | 136.07 ms | 0 | 0 |

每组均核对了进网总数、转发数、分类调用数、异常记录数和命中分数样本数。全部入库，无正常请求明细。结束时 Redis 仅保留最后一个已提交批次作为游标边界，待消费积压已清空；全量拦截的瞬时峰值为 239 个批次，结束时压测进程 Go 活跃堆约 29 MB。

最初全量命中只能跑到约 1,841 RPS；分析发现重复去敏与过大的消费批次造成阻塞，修复后才达到目标。没有通过丢记录或跳过真实写入提高吞吐。

### 验收边界

这些是单机、固定响应、10–30 秒的性能结果，不是长时间生产容量承诺。更大历史、持续流式连接、复杂规则、远程存储或集中出现的敏感文本会改变成本。1 MB 历史仍需完整解析，本次未宣称这一大小能达到 5,000 RPS。

内存队列在强制终止进程时有数据丢失窗口；Redis AOF 使用 `everysec`，主机崩溃还可能丢失最近约一秒写入。Redis 与本地磁盘同时不可写时保留批次重试，队列满后会反压请求。备份/恢复须协调 PostgreSQL、Redis 和本地暂存卷。

### 复现

使用独立 PostgreSQL 数据库和独立 Redis 测试库。测试会清空其中的数据。

```sh
cd gateway
export TEST_DATABASE_URL='postgres://user:password@localhost:5432/sael_test?sslmode=disable'
export TEST_REDIS_URL='redis://localhost:6379/15'
go test -race ./... -count=1

SAEL_LOAD_TEST=1 SAEL_LOAD_MODE=mixed SAEL_LOAD_RPS=5000 SAEL_LOAD_SECONDS=20 \
  go test ./internal/store -run '^TestGatewayLoad$' -count=1 -v
```

`SAEL_LOAD_MODE` 可选 `disabled`、`clean`、`mixed`（5% 拦截）、`hit`、`sse`；`SAEL_LOAD_BODY_BYTES` 设置文本大小。基准与压测应串行运行，避免构建或其他压测抢占 CPU。

集成测试覆盖重复发布/消费、事务中途失败后的回滚与重放、Redis 断线暂存及去敏、配置跨实例同步、冻结迁移和到期、异步入队、正常退出排空，以及 RPM 滚动窗口和筛选。SSE 测试确认首块在上游结束前已经抵达客户端。

总览已在 390 × 844 和 1280 × 720 视口实测：图例随宽度自动换行，曲线按图例实际高度避让；手机显示两行，桌面恢复一行，没有图例横向溢出或文字重叠。RPM 主值为最近一分钟，历史图按时间桶显示 RPM。

## 资料依据

- [Go net/http](https://pkg.go.dev/net/http)：Client / Transport 应复用，连接池与业务并发上限含义不同。
- [Go ReverseProxy](https://pkg.go.dev/net/http/httputil#ReverseProxy)：缓冲池及流式 flush 行为。
- [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)：持久消息流和消费进度。
- [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)：通知会丢失，不能充当可靠日志或唯一配置同步机制。
- [Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)：AOF 的刷盘配置决定故障丢失窗口。
- [pgx BatchResults](https://github.com/jackc/pgx/blob/master/batch.go)：批量减少往返，需要检查 Close 返回的错误。

资料通过官方文档、Context7 与本地依赖源码交叉检查。普通 pipeline 只减少往返，不意味着多条命令原子执行。
